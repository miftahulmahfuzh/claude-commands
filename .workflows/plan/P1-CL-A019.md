# P1-CL-A019 — Every session ends with a ready-to-paste command for the next one

**Card:** miftahulmahfuzh/claude-commands#1
**Branch:** `task/1-every-session-ends-with-a-ready-to` (base `origin/main` @ `05233202`)
**Round:** 1
**Date:** 2026-09-01

## The requirement

`/analyze` produces a plan set of N phases. Walking it from phase 1 to phase N currently
requires the user to remember what comes next. Every command that ends a session should
print a **ready-to-paste command for the next session**.

The user's example: a session that ran `/do P1-AC-A001` should end by printing
`/do P1-AC-A002`. And `/analyze` should end by printing the command that starts phase 1.

## What was actually there before this change

| File | Before |
|---|---|
| `commands/do.md` | Success message printed task, package, files, commit, branch — and stopped. **No next command at all.** This was the real gap. |
| `commands/implement.md` | Termination's "Phase done, more remaining" already printed `/do {TaskID of phase N+1}`. Only that one branch — `--all`, drift and blocked exits said nothing. |
| `commands/analyze.md` | Termination printed `cd <worktree>` + `/implement -f <SLUG>_PLAN.md`, not naming phase 1. |
| `agents/completion-handler.md` | Already computes `next_task_id` (step 2b unblocks it) but never returns it. |

## Approaches considered

| # | Approach | Verdict |
|---|---|---|
| 1 | **`completion-handler` returns the next command; `/do` and `/implement` print what it returns. `/analyze` emits its own.** | **Chosen.** |
| 2 | Each command's Termination block derives the next TaskID itself | Rejected — three copies of one rule, and `/do`'s main context would have to read the plan index and `todos.md`, which is exactly what the subagent pipeline exists to prevent (`commands/do.md` § Context Isolation). |
| 3 | A new `next-command-emitter` subagent | Rejected — a whole agent file, a whole dispatch, for one line of output. Nothing in the repo is that granular. |

Scored against the repo's own criteria:

- **Convention** — `completion-handler` is already the shared tail of both pipelines, and
  `CLAUDE.md` explicitly says a change to one of `/do` / `/implement` should be checked
  against the other. One producer satisfies that by construction.
- **Scope** — approach 1 adds one output field and three Termination edits. Approach 2 adds
  the same three edits *plus* duplicated derivation logic.
- **Verifiability** — the repo has no test runner, so the gate is `./sync.sh` plus reading
  the rendered markdown. A single producer is the version a human can check by reading one
  file instead of three.
- **Reversibility** — one commit either way.

## Ambiguity calls

- **`--phase 1` vs. the bare command in `/analyze`'s termination.** The bare
  `/implement -f <SLUG>_PLAN.md` auto-advances to the lowest incomplete phase, so it stays
  correct if pasted late; `--phase 1` names what the user asked for ("start the first
  phase") and cannot be misread. Chose `--phase 1`, and hardened `/implement` Step 4 to
  refuse an explicitly-named phase whose task is already complete — which removes the only
  thing the bare form was safer about.
- **A `/do` task that is not a plan-set phase.** There is genuinely no next task to name, so
  nothing is printed. Inventing a suggestion ("maybe run /analyze next?") would be noise on
  every EASY task. The narrow reading: the user's example is a sequence, and only sequences
  get a hand-off.

## The shape, used identically in all three commands

A label line saying what it starts, then the command alone on its line so it can be
selected and pasted, with `cd` first where a worktree is involved:

```
Next — phase 2 of 4, in a new session:

  cd <worktree>
  /do P1-AC-A002
```

Nothing may follow the command on its own line — a trailing `# comment` would be parsed as
arguments to the slash command.

## Steps

1. `agents/completion-handler.md` — add `next_command` to the final report: derive it from
   the plan set it already read in step 2b. Empty when there is no next phase.
2. `commands/do.md` — Success message gains the Next block, fed by the handler's report.
   Last phase prints the merge line instead. Non-plan-set task prints nothing.
3. `commands/implement.md` — keep the existing block; give the `--all`, drifted and blocked
   terminations a next command too; harden Step 4 against a completed `--phase N`.
4. `commands/analyze.md` — Termination names phase 1 explicitly.
5. `./sync.sh`.

## Verification

The repo has no CI, no lint and no test runner (`CLAUDE.md`). The gate is:

- `./sync.sh` exits 0 and lists the four changed files
- the four files are read back and the Next blocks are consistent in wording
- `python3 ~/.claude/skills/task/todos.py validate` still passes

## Rollback

One commit. `git revert` it; nothing else depends on the new field, and a
`completion-handler` that reports an extra line breaks no caller.
