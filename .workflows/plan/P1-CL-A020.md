# P1-CL-A020 — /do executes an adopted plan file instead of re-summarizing it

**Card:** miftahulmahfuzh/claude-commands#3
**Branch:** `task/3-do-should-execute-an-adopted-plan-file` (base `origin/main` @ `eb18a6bd`)
**Round:** 1
**Date:** 2026-09-01

## The requirement

> there is a redundancy going on right now. i expect `/analyze` to generate several
> ready-to-execute dedicated implementation plan files. if we execute `/do` from an analyze
> result, we should not run plan-generator again. we just execute the cooked plan file. the main
> thing is how `/do` can detect if this task is generated from analyze or not. if analyze
> generated tasks in todos.md, then it must include the path to the implementation plan file in
> that task description.

## What was actually there before this change

The detection half of the ask was **already built**, so the work is not where the card's first
reading suggests:

| Piece | State before |
|---|---|
| `commands/implement.md:105` | Every phase task already carries `- **Plan**: \`.workflows/plan/{TaskID}.md\`` — plus `**Plan Set**:` and `**Satisfies**:`. The path *is* in the task description. |
| `agents/task-locator.md:28` | Already parses that line, resolves it against `package_path`, and returns `plan_file` **only when the file exists on disk**. |
| `agents/plan-generator.md:25` | Already branches on the plan file and is told to adopt it "without re-planning". |
| `commands/do.md:96` | Already documents the adopt branch. |

One correction the card carries into the work: **`/analyze` does not write tasks into
`todos.md` — `/implement` does.** `/analyze` writes `.workflows/plan/<slug>/phase-{N}.md` inside
a worktree plus a `<SLUG>_PLAN.md` index; `/implement` Step 3 mints the TaskIDs and copies each
phase plan to `{pkg}/.workflows/plan/{TaskID}.md`. So the "put the path in the task description"
requirement belongs to `/implement`, and `/implement` already keeps it. Nothing to add there.

### So what is the actual redundancy

`/do` "adopts" the plan by handing it to an **opus** subagent whose output schema has nowhere to
put code. The brief in `do.md:107-128` is `target_files` + a 2–3 sentence `approach` + `steps`.
A phase plan's value is its complete code blocks; they are read by `plan-generator`, compressed
to prose, and the main context — which is the thing that actually writes the code — never sees
them. That is not redundancy alone, it is **lossy**: the reconciliation `plan-reconciler`
performed across phases is summarized away by an agent that cannot see the other phases.

And the asymmetry is the tell. `/implement` Step 4 (`implement.md:141`):

> Read that phase's plan file and apply its steps in order. The code blocks are complete by
> construction; use them.

Same artifact, same execution, no `plan-generator` and no `context-loader`. CLAUDE.md explicitly
says `/do` and `/implement` share this pipeline pattern and that a change to one should be
checked against the other. On this point they had already diverged.

## Approaches considered

| # | Approach | Verdict |
|---|---|---|
| 1 | **Adopted path: skip `context-loader` and `plan-generator`; the main context reads the plan file and applies it.** | **Chosen.** |
| 2 | Keep `plan-generator` on the adopted path, but have it emit a pass-through brief (`plan_path` only) that the main context then reads. | Rejected. An opus round-trip that adds a filename the locator already returned. Two hops to reach the same file. |
| 3 | Keep isolation intact and have `plan-generator` emit an *extended* brief that embeds the plan's code blocks verbatim. | Rejected. Doubles the tokens (plan read once, re-emitted once), and creates a second copy of the plan that can drift from the file on disk — the two-provenances problem this repo exists to prevent. |

Scored against the repo's own criteria:

- **Convention** — #1 is not a new shape, it is `/implement`'s existing shape. #2 and #3 invent one.
- **Scope** — #1 removes two dispatches and adds no artifact. #3 adds an output schema.
- **Verifiability** — this is a markdown repo, so the gate is `./sync.sh` plus internal-consistency
  greps; #1 is checkable by reading the two commands side by side and seeing them agree, which is
  precisely the check that failed before.
- **Reversibility** — one commit for all three.

## The ambiguity call

The card left one question open: does the main context reading a plan file break the
**main-context-is-code-only** invariant (`do.md:193`)?

**Decision: it does not, and the invariant is being stated more precisely rather than weakened.**
The rule exists to keep the main context small *during code edits* — that is why it names
`todos.md`, `package_readme.md` and `analysis_report.md`, which are background documentation. A
plan file is not background: it is the instruction set for the edit, and it is the one document
the executor cannot do its job without. `/implement` has always read it in the main context and
its Context Management diagram (`implement.md:271-273`) says so out loud.

The narrower reading — "the main context reads nothing at all, so the brief must carry
everything" — was considered and lost, because it is the reading that produces the lossy
summarization in the first place. It is recorded here so a later session can see it was weighed.

The invariant is therefore restated as: **the main context reads exactly one plan file, the
adopted one, and no other `.workflows` file.** That is checkable, and it is what both commands
will now say.

## What changes

### 1. `commands/do.md` — Phase 1 forks

Insert a gate immediately after `task-locator` (Step 1) and before Step 2, so the pipeline
chooses its route on the locator's output:

- `plan_file` non-empty → **adopted path**: skip Step 2 and Step 3 entirely, go to Phase 2 with
  the plan file path.
- `plan_file` empty → **brief path**: Step 2 and Step 3 as they are today, including the HARD
  refusal.

The HARD refusal is untouched by this: the adopted path is by definition only taken when a plan
exists, so the case the refusal guards (`HARD`, no plan) always lands on the brief path where
`plan-generator` still lives. There is no gap to backfill.

`--note` on the adopted path is applied by the main context on top of the plan, and never
overrides it — the same rule `implement.md:17` states for its own `-note`.

### 2. `commands/do.md` — Phase 2 gains a read

Phase 2 currently opens with "Display the task summary from the brief". On the adopted path it
opens by reading the plan file and applying its steps in order, with the plan's own Verification
commands as step 3. Drift handling (`do.md:214-218`) already covers what happens when the tree
has moved under the plan, and now applies directly rather than through a summary.

### 3. `commands/do.md` — the Context Isolation table

The row for the main context changes from "target files only" to "target files, and the adopted
plan file". The paragraph beneath it (`do.md:193`) is restated as above: never `todos.md`,
`package_readme.md` or `analysis_report.md`; exactly one plan file when there is one.

### 4. `commands/do.md` — progress messages

The adopted path prints fewer lines, and says why:

```
🔍 Locating task... (task-locator)
📁 Found: P1-TC-A002 in tools/toolcore/.workflows/todos.md
📖 Adopting plan: .workflows/plan/P1-TC-A002.md  [context-loader + plan-generator skipped]

🎯 Executing: P1-TC-A002 (main context)
```

### 5. `agents/task-locator.md` — report which dependencies are incomplete

`plan-generator` step 4 currently owns the `depends_on` check, which means on the adopted path
nothing would own it. Rather than duplicate the check into the main context — which would mean
reading `todos.md` there, the exact thing the pipeline forbids — it moves **up** into the locator,
which is already reading every `todos.md` in the repo and is haiku.

Add to the output:

```yaml
  depends_on: ["{TaskID}"]
  depends_on_incomplete: ["{TaskID}"]   # the subset not marked - [x] under ## Active Tasks
```

Parsing note for the agent: a TaskID legitimately appears several times in one file (the rolling
summary and the `## Recent Activity` log echo it), so completeness is read from the entry under
`## Active Tasks` / `## Completed Tasks`, not from the first line that matches.

This is a strict improvement on both paths: the blocked-task refusal now fires after one haiku
call instead of after two opus calls.

### 6. `agents/plan-generator.md` — refuse a task that has a plan

Its step 1 stops being "adopt it" and becomes a refusal:

```yaml
status: error
reason: plan_exists_use_adopted_path
message: |
  {TaskID} has a plan file at {path}. /do executes it directly in the main context;
  plan-generator must not be dispatched for a planned task. This brief would have
  summarized complete code into prose.
```

Keeping the adopt branch as a working fallback is what would let the lossy route quietly return
the next time someone edits the fork. A refusal makes there be exactly one way to execute a
planned task.

Steps 2 (brief for EASY/NORMAL) and 3 (HARD refusal) are unchanged. Step 4's dependency check is
deleted, having moved to the locator.

### 7. `commands/implement.md` — one cross-reference line

No behavioural change; Step 4 already does the right thing. Add a sentence to Step 4 saying `/do`
adopts the same plan file the same way, so the two stay tied when the next person edits either.
This is the parallel-change check CLAUDE.md asks for, and the answer is "already aligned, now
written down".

### 8. `CLAUDE.md` and `README.md`

- CLAUDE.md's "Subagent pipeline pattern" numbered list documents the 7-step `/do` flow; it gains
  the fork, so the file describing the invariant does not contradict the command implementing it.
- README.md:148-155 describes the same pipeline for users; same edit, shorter.
